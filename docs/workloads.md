# 用性能用例定位瓶颈

第一次在一台机器上测量时，可先跑 `@survey`。它覆盖加载后的小请求、prefill 吞吐、真实编码提示词、长解码、混合批次、前缀对照和突发流量。根据报告中的异常再展开对应的用例族。命令在解压后的部署目录执行。

```bash
./benchmark.sh --list --range @survey
./benchmark.sh --hardware a2 --model /models/DeepSeek-V4-Flash-0731-w8a8 \
  --range @survey --results /data/results/round01
```

内置目录有 242 条用例。`--range` 可以使用单个 ID、含端点的范围、用例族，或逗号分隔的组合。编号只承担定位和分片的作用。例如 `@prefix,218-223,9` 在同一进程里执行所选用例，共用加载好的模型。重叠选择会去重。运行前可用 `--list` 查看实际的输入长度、输出长度、并发、请求数、预热数、前缀和到达参数。没有设置 `--range` 时运行整套内置用例。

| 要回答的问题 | 选哪些用例 | 对照哪些观测 |
| --- | --- | --- |
| 常见慢点出现在哪里 | `@survey`，即 1、6、9、211、220、227、228、238 | 先看计时阶段的吞吐、TTFT、TPOT 和尾延迟，再查对应 rank 的热点形状 |
| prefill 在哪些长度或并发开始失速 | `@shape` 包含 10–201，输入 128/129、512/513、2048/2049、8192/8193，输出 1/16/64/256；`@prefill` 还包含 202–209 的 16383/16384/16385 和 32767 token | 固定输出为 1，比较相邻长度及并发的输入吞吐、服务端 prefill 时间、内核调用次数、tiling 与芯片间负载 |
| 长解码单步耗时随历史长度或并发怎样变化 | `@decode-steady` 选中 210–217，最多生成 2048 token；`@decode` 也包含基础解码用例 | 看 TPOT、KV 占用、设备时间和访存带宽。分析实际长解码形状时加 `--profile` 完整重放，默认短重放最多生成 8 token |
| 混合批次是否使短请求被长请求拖慢 | `@mixed` 包含原用例 7 以及 218–223。流量中有短输入短输出、长输入短输出、短输入长输出；222–223 交替发送 256→512 和 8192→1 的请求 | 同时查看汇总延迟和 `measurement.by_request_shape` 中每类请求的 TTFT、TPOT、E2E 样本数和分位数，再查调度队列 |
| 公共文档或代码前缀被复用后能节省多少计算 | `@prefix` 的 224–232 按并发 1/8/32 分组，各组依次测试独立输入、1 个公共前缀及轮转的 8 个前缀 | 输入长度固定 4096，输出 32，公共部分为 3840 token。用同一并发的独立输入作对照，看 `server.prefix_hit_fraction`、prefill、TTFT 和算子耗时 |
| 服务何时跟不上到达速率，突发是否放大尾延迟 | `@arrival` 的 233–242 覆盖 4–200 请求/秒的预定流量，237–240 固定平均每秒 32 请求，以 4/8/16/32 请求一批抵达 | 比较实际完成速率、`client_issue_lag_ms`、`scheduled_e2e_ms`、运行与等待队列、KV 占用和抢占 |

### 如何解释对照

- `@shape-in512` 是按用例名的连字符边界选中的子族，可进一步缩小矩阵。`@survey` 则按上述八个已命名用例匹配。在自定义目录里同样可用 `@名称` 选择该名称或以 `名称-` 开头的用例。
- 混合请求按索引轮转。以用例 220 为例，输入长度 `[128,128,128,8192]` 与输出长度 `[16,16,256,32]` 逐项配对，短交互请求占一半。单 token 输出只有 TTFT 和 E2E，TPOT 会记为空。
- `@prefix` 让同一阶段同一个前缀组里请求的前 3840 个 token 完全一致，后缀独立。每个用例、预热、正式计时、流水线及访存重放均使用独立的前缀，正式计时包含该阶段首次填充缓存的代价。前缀按请求轮转，跨数据并行副本时实际命中情况由路由和引擎缓存决定。查看该段已导出的命中与查询增量；缺失计数时不能推断实际命中。
- 默认短重放保留输入形状、压缩输出长度，混合输出的每一项最多取 8。前缀用例会保留多波请求以观察复用。两组 PMU 采用独立重放，权重、长度和并发配置相同，私有 token 与前缀的取值不同。MoE 的实际路由和批次可能不同，比较时核对各次 trace 中的形状和调用次数。
- `@arrival` 对每一阶段单独建立目标时间表，限制最多 64 个在途请求。慢请求占满并发时，后续请求延后发出，延迟量会记录到逐请求的 `client_issue_lag_ms`。`scheduled_e2e_ms` 从预定抵达时刻计算，含客户端迟发和服务端响应耗时。普通 `e2e_ms` 从实际发送前计算。观察到持续迟发时，实际到达率可能低于设定值。
- 这些输入测试引擎负载与设备行为。需要同时检查生成精度时加 `--golden`。同一优化的前后对照使用相同机型、模型、用例 ID、采样模式和配置，保留各轮原始结果。

### 超长上下文

单独随包提供 `benches/extended-context.json`。1001–1010 依次按 65,536、131,072、262,144、524,288、1,048,576 的**输入与输出总长**分成五组，每组输出长度分别为 1 和 128，并发为 1。这组用例按实际 checkpoint 配置、KV 缓存预算和单机显存单独选择。下面的命令只选择 64K 的两条。

```bash
./benchmark.sh --list --cases ./benches/extended-context.json --range 1001-1002
./benchmark.sh --hardware a2 --model /models/DeepSeek-V4-Flash-0731-w8a8 \
  --cases ./benches/extended-context.json --range 1001-1002 \
  --results /data/results/long -- --max-model-len 65536
```

自定义 token 用例支持三个可选字段。`output_pattern` 与 `input_tokens` 逐项配对，最大值须等于 `output_tokens`。`shared_prefix` 包含 `tokens` 和 `groups`，每条输入需留出私有后缀。`arrivals` 包含 `burst` 和 `interval_ms`，表示每隔多少毫秒计划发出一批多少个请求。省略这些字段时沿用独立输入、固定输出长度、按并发填补已完成请求的行为。
